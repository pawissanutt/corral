# T-758 R1 — history work fixes and live measurements

History budgets pass, but the absolute command targets are not met. Q2's owner-delivered
PM answer accepts the history-independence fixes with the measured active-workload latency
limitation, explicitly requiring every safety probe to remain. Review F1's separate RSS
requirement is now addressed: the matched read-only probe shows **27.0% lower final RSS**
(84,748 → 61,864 KiB) after unused refresh-buffer pages are released on Linux/glibc.
The post-rebase quick gate for each submitted tree is recorded separately in its run receipt.

## Implemented

- SQLite open-board/list queries use the open-task partial index, not a terminal-task
  table scan. Exact-token row reads drive the token index before point-reading documents;
  SQLite previously chose to scan the entire history family, even for a missing token.
  Current/open row reads explicitly use their family-keyed partial indexes.
- BoardDelta state is detached from its read view and cached per database handle, rather
  than in one process-global TUI slot. Checked policy/attention projections have a separate
  cache from tolerant UI frames. Point-head reuse requires the same pinned change sequence
  and an unexpired view. Cache entries do not retain WAL readers.
- Attention, PM inputs and list metadata share those bounded inputs. The header starts
  from backend status counts and applies assessor-computed visual moves; it no longer
  serializes shell tasks or reclassifies/scans the entire task vector for each count.
- Lesson scheduling has an independent preparation cursor from artifact signal previews.
  Coordination no longer derives unused artifact signals or landed-path Git diffs.
  Explicit signal previews still receive their own complete invalidations.
- After a replacement frame retires its predecessor, Linux/glibc returns unused allocator
  pages via its thread-safe advisory trim. Live data/caches and safety checks are unchanged;
  this runs at refresh completion, never in paint/input handlers. Other targets remain no-op.

### Review changes round 1 — F1: material RSS reduction

The first review correctly rejected the 0.45% RSS difference above. Q2 waives absolute
latency, **not memory**. No RSS waiver is used.

Two competing explanations were tested: retained live board/cache data versus allocator
high-water retention of freed refresh buffers. A short task-owned diagnostic used `mallinfo2`
after the same two ordinary refreshes. RSS was 86,948 KiB, but live libc allocations were
only 29,784,960 bytes and free arena space was 37,999,744 bytes. A diagnostic advisory trim
reduced RSS to 62,304 KiB **without dropping any board state**. Dropping the board/context
subsequently reduced live allocations to 1,428,944 bytes, but resident pages still remained
near 62 MB: the measured excess is predominantly allocator retention, not live task data.
The diagnostic, including its FFI, stays in scratch; it is not a new committed test.

The production fix in `board/snapshot.rs` releases those unused pages immediately after
frame replacement, when the previous task/head/index vectors and conversion buffers are
retired. It does not evict live caches, change read-view lifetimes or remove a safety probe.
`malloc_trim(0)` is thread-safe, advisory, and requires no pointer/lifetime preconditions.
It is compiled only for Linux/glibc; no global allocator, environment policy, dependency or
non-GNU behavior changes. Peak allocation can still contain two frames; the fix returns
unused pages between refreshes rather than retaining that peak for the board's lifetime.

## Regression evidence

- Failing-first SQL regression over **2 and 8** history rows: before, open-board VM work
  68/98 steps, open heads 66/96, missing token 41/113, matching token 50/122. After, exact
  equality at both sizes (79/79, 77/77, 20/20, 38/38 respectively). The final regression also
  covers current-row sibling-family growth. It counts actual SQLite VM instructions, not
  just successfully decoded documents.
- Header regression failed first at 15 unchanged head decodes; it now requires **zero**
  during header reload while preserving blocked/slot counts.
- Scheduling regression failed first at one historical run decode; schedule-only preparation
  now reads zero historical signal documents, and later explicit previews still match the
  existing full-task oracle after changes.
- Existing incremental-board test now exercises both caches, changed-task-only reads,
  current-view rebinding, terminal departure and fail-closed corruption behavior.
- `cargo nextest run --lib -p corral-tui --features corral-core/test-clock --run-ignored only
  -E 'test(=app::hot_budget::hot_reads_work_stays_independent_of_history)'`: PASS, 6.939 s.
- Targeted core/ops/TUI nextest selection: **40/40 PASS**, 14.461 s suite execution.
- `cargo fmt --all`, `git diff --check`, and worktree SLOC check: PASS; maximum 800 SLOC.
- Changed-file LSP requests returned zero diagnostics but `complete=false`; these are not
  claimed as completed checks. Rust builds/tests above completed successfully.

Two new cheap regressions were added; existing board/header tests were extended. No new
end-to-end or slow test was added. The first quick gate reported +2 Rust registrations and
both additions unmeasured at its initial cost-report stage; no >30 s added-suite claim is made.
These targeted tests do not replace the contracted gate.

The first quick gate passed formatting, SLOC and Clippy, then found three derived-row integration
regressions. Hypotheses were a cache-induced work change versus cold scheduling preparation
inside the sync HotScope. The latter was confirmed: announcement preparation still initialized
the old signal cache, while the scheduling reader cold-built its separate cache inside HotScope.
It now prepares coordination explicitly, and announcement identities are read from that same
scheduling root. The legacy-cursor upgrade fixture now writes its old-format cursor to the
coordination cache actually used by PM; none of its oracle, equality or work assertions changed.
The unchanged five-test `derived_rows_entries` integration suite then passed. The replacement
quick gate passed 1,875/1,875 tests; final added-test cost was 2 registrations / 0.311 s with
zero unmeasured additions. Review then requested the distinct RSS correction above, whose

## Remaining decision and limitations

Q2's accepted option is delivery of these history-independence improvements with the measured
active-workload latency limitation. The PM explicitly says to keep every safety probe and not
redesign candidate-safety probing in this task. No such redesign was made. Measurements name
their exact pre-rebase product revision; the final rebase incorporates main's separate runtime-skew
fixes and the contracted quick gate checks the resulting tree. The approved matched short
probe now demonstrates material RSS improvement on this Linux/glibc host. That is not a claim
about other allocators/platforms or the full live sync/autopilot process: no candidate live-board
restart or long-running soak was performed.
