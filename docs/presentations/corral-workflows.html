The board lifecycle

Select a status to see every scenario that passes through it. Ideas render inside the Backlog column; Dropped is off the main path.

  1. IdeaCaptured owner intent. Never dispatchable until promoted.
  2. BacklogFiled work. Eligible for auto_backlog unless held.
  3. ReadyAuthorized, waiting for dependencies, capacity or admission.
  4. RunningA run holds a slot. Declared external waits stay here.
  5. Needs meOwner question, escalation or uncertainty to inspect.
  6. ReviewAfter corral done: gate, reviewer, acceptance.
  7. DoneAccepted. Landed, or a kept branch. Hooks decide readiness.
DroppedDiscarded, declined or merged. History retained.
Autopilot stages are separate from board statuses: gating, reviewing, reviewed, landing and blocked usually accompany Review; changes returns work to Running, or Ready when a fresh retry is queued; escalation moves it to Needs me.

01The PM is optional

One workspace PM coordinates through read-only pm brief / pm next cards. Sync, workers and independent reviewers work without it.

02Sync drives automation

The board, a plugin hook or corral sync --watch. With no driver automatic queues and reviews wait; workers keep running.

03corral done means Review

Not landed, not Done. herdr idle or done labels never finish a task.

04Landed is not operational

Opt-in post-land hooks prove readiness. A failed hook blocks dependent admission but never unlands the commit.

        Appendix: a lead PM and project PMs

        This is design input only. It is not in the 85-scenario count, has no controls here, and no command for it exists. Today Corral has exactly one optional workspace PM: state/pm.json holds only a pane_id, and that pane is not lease evidence.

        Proposed lease scopes
        Proposed lease scopeAuthority and inbox
        leadOwner conversation, project triage, cross-project dependency proposals, priorities and limits. Digest/escalation inbox.
        project:<key>That project's planning, dispatch, replies and change requests, review initiation and policy-permitted landing. Project event inbox.

        Scopes do not overlap. The lead lease is not a wildcard over project tasks. Existing sync, admission, autopilot, gates, reviews, session ownership and post-land receipts stay authoritative.

        1. Owner → lead The owner talks to the lead about priorities and cross-project work.
        2. Lead Proposes linked single-project tasks. There is no multi-project task model; dependencies express order.
        3. Lead → project PM The proposal reaches the holder of that project's lease through its inbox.
        4. Project PM Applies its own task changes within its disjoint project lease.
        5. Unmanaged project The lead must explicitly acquire that project's lease; status shows each lease separately.
        6. Future design Lease fencing and takeover and the summary/escalation channel are not specified as shipped behavior.
