Part 1 Executive summary

The one-paragraph version

Corral’s engine was replaced with a much smaller one, and the daemon, the pi agent host and the app were moved onto it. The work landed on main on 18 November 2026. The new engine runs a task from creation to a landed commit without any agent managing it, lets the owner get past any check with one command, and runs a gate once per commit. It passes its tests and a real end-to-end run. It has not yet been used on a product repository, and the old engine’s source is still in the tree, unbuilt, waiting for the cutover.

Why it was done

Measured on the workspace store, 17 November 2026: 976 tasks, 621 landed with full history. These measures are the reason for the whole rework.

What changed for the owner

  • No state needs an agent. The owner clears any state with one command. The assistant is optional.
  • Force is one flag. Dependencies, slot limits, the gate, status rules and a live session can each be passed with --force on the same command. Every refusal names the command that gets past it.
  • A gate runs once per commit that is landed or sent back. A green rerun clears a red one. No tiers, attempts ledger, credits or receipts.
  • A paired device is the owner. Per-device authority classes, previews and proofs are gone.
  • One chat assistant replaces the PM and the assistant. A plan is a parent task with children and a Markdown document.

What is not done

  • The cutover. The new programs are still named corral-next and corrald-next, state lives in .corral-next/, the four old crates are still in the tree (out of the workspace, unbuilt), scripts/gate.sh still targets them, and the README and docs/DESIGN.md still describe the old engine.
  • Real use. The exit criteria have not been shown on a product repository.
  • Old-system work on this repository is stranded. See Consequences of landing in Part 4.
  • Three things only you can do: enrol the terminal app, pair your browser, and try one task. See 3.1.

Decisions waiting on the owner

  1. When to finish the cutover: rename, delete the old crates, replace the gate scripts, rewrite the README and design document.
  2. What to do with the stranded old-system branches: land their still-relevant parts by hand, or drop them.
  3. Whether Artifacts stays its own destination in the app or becomes an overlay.
  4. Whether the two app features that have no successor yet are wanted: the welcome tour, and launching corral-pi from the app.
  5. When to stop the old daemon. Until then both boards hold the same 171 open tasks.

Part 2 High-level overview

The five rules the new engine follows

  1. The owner clears any state in one action. No state exists that only an agent can leave.
  2. Green is green. A check passes or fails on a commit.
  3. One trust boundary: the network. The local user is the owner. Only paired remote devices authenticate, and a paired device is the owner.
  4. State stays readable. Tasks, runs, checks, artifacts, events. Nothing derived is stored.
  5. Every refusal names the command that gets past it, including its --force form.

The landing itself

  • main had moved by ten commits of Build work (API profiles, uncapped metering, repair of a failed landing gate). They were merged into the branch first.
  • Ten files conflicted, all in the pi host and its build guide. The changes to corral-ops and corral-core merged untouched.

  • Dropped: edits to the launch message, paid capability, approved bindings and profile catalog, because that machinery no longer exists.
  • Not carried: the [build.api] default mapping of child presets to API profiles. In the new host a child profile names its API connection directly.
  • The old crates had stopped compiling on the branch when the wire was replaced, so they were taken out of the workspace. The owner chose to keep their source in the tree for now.

3.3 Set up a workspace

Terminal
$ corral-next init
Initialized <workspace>/.corral-next

init writes a corral.toml with every setting commented out. Add one table per Git repository, and a profile for the agent you use:

corral.toml
[defaults]
profile = "pi-worker"          # worker profile when nothing else names one

[projects.app]
path = "app"                   # relative to the workspace root; "." for the root itself
gate = ["just check"]          # optional; each line runs with sh -c in the task's worktree
reviewer = "pi-worker"         # optional; a reviewer runs after a green gate

[profiles.pi-worker]
harness = "pi"                 # built in: omo, omp, claude, pi, generic
model = "openai-codex/gpt-6.1-sol"
effort = "high"
Terminal
$ corral-next config check
Configuration is valid

Settings worth knowing (all optional):

SettingDefaultMeaning
limits.running4Tasks in Running or Blocked at once. Review, reviewers and gates hold no slot.
defaults.auto_dispatchfalseStart Ready tasks by themselves when a slot is free.
defaults.auto_landfalseLand after the gate and review without asking you.

3.4 A task from start to landed

Run with a scripted agent that writes one file and calls done:

Terminal
$ corral-next new "Add a note" -p app --ready
T-001: ready — Add a note

$ corral-next dispatch T-001
T-001: running — Add a note
worker R1: <workspace>/app/.worktrees/T-001

      (the agent works in that worktree, then runs
       corral-next done T-001 --summary "Added a note")

$ corral-next wait --for ready --task T-001 --timeout 1m
8 2026-11-19T04:20:16Z ready auto T-001 R1 {"sha":"ce0d6944…"}

$ corral-next show T-001
T-001: Add a note
Status: review    Priority: P2    Round: 0
Checks:
  gate ce0d6944…: Pass
Artifacts:
  T-001:1  129 B  diff     diff.patch
  T-001:2   12 B  summary  summary.md
  T-001:3   20 B  gate     gate-ce0d6944.log

$ corral-next approve T-001
T-001: done — Add a note

$ git -C app log --oneline
ce0d694 T-001 Add a note
126d00d base

What happened, in order:

  1. new created the task. --ready puts it in Ready; without it the task starts in Backlog; --idea starts it as an Idea.
  2. dispatch made the worktree app/.worktrees/T-001 on branch corral/T-001 and started the agent.
  3. The agent’s done committed its work, stored the diff and summary, and moved the task to Review.
  4. The gate ran at once on that commit and passed. With a reviewer configured, the review would run next.
  5. ready means the task is waiting for you. approve rebased, fast-forwarded the base branch, removed the worktree and branch, and set Done.

With auto_land = true step 5 happens by itself.

3.5 When a task stops

A Blocked task always says why and what clears it:

What happenedWhat you run
The agent asked a questioncorral-next reply <id> "<text>"
The agent’s session ended without donecorral-next retry <id> (add --profile <p>, --fresh to start over from the base, or --note "<text>")

You give up on the taskcorral-next drop <id>; corral-next reopen <id> brings it back to Backlog

3.6 Getting past a refusal

A refusal exits with status 2 and prints the commands that get past it:

Terminal
$ corral-next dispatch T-003
refused: dispatch blocked by dependencies
next: corral-next dispatch T-003 --force
next: corral-next move T-002 done --force

$ corral-next dispatch T-003 --force
T-003: running — Second part

The forced action is recorded:

Terminal
$ corral-next log T-003
SEQ  KIND        ACTOR  RUN  DETAIL
12   dispatched  owner  R1   {"base":"main","profile":"script"}
13   forced      owner  R1   {"operation":"dispatch","skipped":["dependencies"]}

Force does not get past something physical. The refusal then names a command that can work:

Terminal
$ corral-next approve T-003 --onto nosuchbranch
refused: landing target branch "nosuchbranch" does not exist
next: corral-next approve T-003 --onto main

The real next: lines print the full path of the corral-next binary; it is shortened here. The log output is shown without its time column.

3.10 Agents with corral-pi

  • Sign in once with corral-pi login. An API key is a separate connection: corral-pi login --connection anthropic-api.
  • A task uses Pi when its profile has harness = "pi".
RoleHow it startsWhat it does
Workercorral-next dispatch <id> --profile <pi-profile>Edits the task’s worktree and submits with done
ReviewerSet the project’s reviewer profileRecords approve or changes; the next round goes to the same conversation
AssistantAsk in the app, or corral-pi chat --dir <session-dir>Chats, and can run the same commands you can

  • Controls: Cancel stops the current turn. Pause also holds automated input such as gate notes; Resume delivers it. A worker saves a checkpoint before each turn, and Rewind restores the worktree and conversation to one.
  • Spending: an API model needs no cap. --max-usd <amount> in a profile’s args sets one. Continuing on an API key after a subscription quota error is opt-in with --paid-route <provider/model> and needs a cap.
  • Build Land: rebase, the project’s gate, fast-forward. If the gate fails, the session is handed the failure and Land runs again when it has committed a fix, at most three times.

Things to know

  • Both boards hold the same 171 open tasks. Automatic dispatch is off on the new board, but the old board can still start an agent on one. Work a task on one board only.
  • It is a one-time copy. The old board keeps running, and a change made there after the import does not come over. Running the import again adds tasks created since and skips the ones already imported; it does not update them.
  • New task ids start at T-2000 on this machine, so an import cannot collide with a task created here first.
  • An imported task that still has a worktree or branch from the old system, such as T-855, is refused at dispatch (“task worktree or branch already exists outside its run history”) until that worktree and branch are landed or removed.
  • The burn-up counts a task as landed only when a commit landed. The 54 tasks moved to Done by hand are in scope and not counted as landed.
  • Closing times: 754 from the old event log, 39 from the task’s own status time, 13 from its last update. Those 13 can be days late.
  • The Usage page stays empty until a new run reports.
  • Undo: the empty store from before the import is in ~/.local/share/corral-next/backups/pre-import-20261118/. Stop corrald-next.service, copy its three files back into .corral-next/, start the service.

3.12 What is gone, so you do not look for it

  • The classic terminal board, the PM role, queue commands and modes.
  • Questions, plans and attention items as separate objects with their own review.
  • Gate tiers, selection, quarantine, attempts and receipts.
  • Authority prompts and proofs on paired devices.
  • In pi sessions: the /plan and /handoff flows, and the [build.api] preset mapping.
  • In the app: the welcome tour, and launching corral-pi from the app. Neither has a successor yet.

Part 4 Technical detail

4.1 One entry point, typed operations

Every operation is one variant of Op. Engine::apply(op, force) is the single entry point for the CLI, the daemon and the pipeline. The CLI parses its arguments into an Op; the wire submits { op, force } unchanged.

Rust
pub enum Op {
    New { .. }, Edit { .. }, Comment { id, text }, Move { id, status },
    Dispatch { id, profile, base }, Reply { id, text }, Stop { id },
    Retry { id, profile, fresh, note }, Done { id, summary }, Gate { id },
    Review { id, profile }, Verdict { id, approve, notes }, Changes { id, text },
    Approve { id, onto }, Drop { id }, Reopen { id },
    ArtifactAdd { .. }, UsageAdd { .. }, Sync,
}

pub struct Refusal { pub reason: String, pub next: Vec<Next>, /* config problems */ }
pub struct Next    { pub op: Op, pub force: bool }

A refusal carries the typed operations that get past it, including the forced form. The app turns each Next into a button; the CLI prints it as a command.

4.2 Force

Force is not a second mechanism. There is one short list of checks and the owner passes any of them.

OperationNormally requires--force skips
dispatchBacklog or Ready, a project, dependencies Done, a free slotDependencies and slots
approveReview, and a green gate on the commit being landedThe gate and the status rule: any task with a branch lands
moveA move among Idea, Backlog, Ready; or Done or Dropped back to BacklogEvery status rule: any status to any status
  • Cannot be skipped: a rebase conflict, a missing branch, a refusal from git. These are physical.
  • Recorded: each forced action appends one forced event listing what it skipped.
  • Automation never forces.

Observed in the browser, paired to a real daemon: moving a Backlog task to Done was refused with “cannot move backlog to done without force”; the sheet offered “Move anyway” and showed corral move T-001 done --force; the event log then held forced {"from":"backlog","operation":"move","skipped":["status rule"],"to":"done"} with the owner as actor.

4.3 After done: the pipeline

done, verdict and gate advance the task at once; nothing waits for a timer.

Pseudocode
while status is Review:
    head = branch HEAD
    gate configured and no gate check for head  -> run the gate; red: send back, stop
    reviewer configured and no review check for this round:
        review already requested this round -> stop (waiting for its verdict)
        reviewer session live -> send it the re-review request, stop
        else start a reviewer whose prompt carries the earlier rounds' notes, stop
    review check is Fail -> stop (sent back when the verdict arrived)
    auto_land -> land, stop
    else -> append `ready` once, stop (waiting for the owner)

A red gate, a “changes” verdict and a rebase conflict all use one send-back path. At the round limit the task becomes Blocked and names changes, retry and approve --force.

4.4 Landing

One function, under a per-repository lock:

  1. Rebase the worktree onto the target. On conflict: abort and send back.
  2. If a gate is configured, not skipped, and no green check exists for the rebased commit, run it. Red: send back.
  3. Fast-forward the target. If it is checked out in a worktree, git merge --ff-only there; if it is checked out nowhere, update the ref. Git decides whether local changes collide.
  4. Close the task’s sessions, remove the worktree, delete the branch, set Done, record landed with the commit.

The target is the branch the run started from, or any existing branch named with approve --onto. Because the lock covers rebase through fast-forward, the base cannot move underneath a landing, so a gate reruns only when the rebase changed the commit.

4.5 Sessions and runners

A session is an id, a worktree, a transcript and a process. One small interface drives every kind of agent:

Rust
pub trait Runner {
    fn start(&self, spec: &LaunchSpec) -> Result<SessionRef>;
    fn status(&self, session: &SessionRef) -> Result<SessionStatus>; // Working, Blocked, Idle, Gone
    fn send(&self, session: &SessionRef, text: &str, origin: Origin) -> Result<()>;
    fn stop(&self, session: &SessionRef) -> Result<()>;
    fn focus(&self, session: &SessionRef) -> Result<()>;
}

Four runners: a herdr pane, a detached process, the pi host, and a fake for tests. A sync pass reads each live session, turns “agent is asking” into a Blocked card that names reply, turns “session ended without done” into a Blocked card that names retry, dispatches Ready work when automatic dispatch is on, and advances stalled pipelines.

Two rules that came out of testing: slots count Running and Blocked tasks, not sessions; and approve does not wait for the worker to go idle.

4.7 Wire and daemon

  • One write command: op.submit { op, force }. The authority field is gone.
  • Of 19 command families, task and review are kept, session and config are reshaped, and 15 are dropped (question, queue, attention, plan, annotation, mode, assistant, message, pm, inbox, knowledge, meta, repair, run, setup). Each dropped family maps onto an engine operation or has no successor.
  • Session controls for chat and agent sessions: cancel, pause, resume, terminate, relaunch, rewind.
  • Pairing: corrald-next pair prints a link, waits for the device, shows its name and six-digit code and asks before enrolling it. Verified in a browser: answering yes pairs the device and the pairing survives a page reload; answering no enrols nothing.

4.8 Pi host

  • One-command launch: corral-pi run, chat, build, login.
  • The host’s Corral tools run the same commands as the owner. A repeated done is harmless.
  • No generations, fences, bootstrap files, receipt caps or capability snapshots. Restarting resumes the transcript.
  • Kept by owner decision: checkpoints and rewind inside the host; a reviewer that keeps its context across rounds.
  • A build session lands locally: rebase, the project’s gate, fast-forward.
  • Repair of a failed landing gate (carried over from main on 18 November): when the gate fails during Land, the host hands the failed command and log to the session and runs Land again once that turn ends with a new commit, at most three times per Land choice.
  • Spending: an API model runs without a cap and its usage is still reported. --max-usd sets an optional cap. --paid-route still requires a cap.
  • Size: 41,488 lines of TypeScript in 276 source files (321 files before), plus 28,519 lines of tests.

4.9 App

  • Destinations: Now, Changes, Plans, Agents, Review, Timeline, Usage, Artifacts, Settings. Inbox merged into Now; Builds merged into Agents.
  • Every task shows its operations (15 in the Actions menu). A refused action opens a sheet with one button per way past it. Destructive actions ask once.
  • Settings edits corral.toml directly.
  • Three forms from one codebase: terminal, web desktop, phone. 101,298 lines of Rust.

4.11 Consequences of landing

  • The old corral no longer builds from main. The installed corral and corral-pi-host binaries keep running.
  • scripts/gate.sh targets the old crates, which no longer compile. It was not rerun after landing.
  • Unlanded old-system branches on this repository are stranded: T-855 (11 commits), T-965 (4), T-977 (3), T-966 (2), T-973, T-974, T-869, A-78, A-92 (1 each), and the build sessions mwl8ran8sv (21) and mwlv2x2nbv (4).
  • The corral-app-tui launcher was updated on 18 November to use the new daemon. See 3.1.
  • The README install line is stale: cargo install --path crates/corral now fails.
  • Undo: the landing is one local merge commit; git revert -m 1 9e098a06a reverses it.

4.12 Known limits

  • Git, session and database effects are not crash-atomic together. A sync pass and the owner’s commands repair a half-finished step.
  • A spending cap can be overshot by requests already in flight.
  • The Claude SDK lane rejects --max-usd.
  • Two clients saving settings at once: the last writer wins.
  • After an operation replies “Running” there is no handle to wait on its completion; the event stream shows it.
  • On the web, a menu opened by pointer ignores the arrow keys; a menu opened by keyboard does not.
  • The terminal form cannot preview images or open an artifact in an external program.
  • Usage totals cover only runs whose harness reports usage; the report says how many runs it covers.
  • Imported history is a summary: one created event per task and one closing event. The old board’s gates, reviews and runs are not in the new log.
  • Fixed after the landing: a corral-pi build session created a directory that hid the old host’s saved logins from every later session. Commit 780c5154f, with a regression test.

4.13 What comes next

  1. Decide the cutover and do it: rename corral-next to corral and .corral-next/ to .corral/, delete the four old crates, replace the gate scripts, rewrite the README and docs/DESIGN.md.
  2. Stop the old daemon when you are ready to work from the new board only. Your tasks are already imported. See 3.11.
  3. Use it on a product repository and check the four exit criteria:
    • With no assistant running, new, dispatch and approve land a one-line change.
    • A landed task runs its gate once per commit that is actually landed or sent back.
    • Every Blocked card carries the command that clears it, and none names an agent.
    • Every refusal names its force command, and the app offers each one.
