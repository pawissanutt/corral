# Same-host Lite–Corral fixture launcher v1 (C1)

This is a contract and set of synthetic launcher inputs, not a launcher, runtime result, or a grant. Consult the separate T-2076 owner disposition before implementing. `T-2069:2` governs lifecycle, policy, accounting and report DTOs; `T-2073:3` governs the February-close broker packet and disclosure conventions. This profile selects specific transport and launch choices without editing either packet. A breaking change to the choices below requires a new launcher version and matching pins in both repos. Compare bytes and SHA-256 values out of band, not via a sibling checkout or a self-authenticating manifest.

## Build and launch

`launcher-v1.json` is the machine-readable profile/lock of upstream inputs and proposed launch interface. `build-manifest-v1.schema.json` and `build-manifest.example.json` describe the C4 Corral package, not a build produced by C1. The Lite runner owns the joint launch and independently verifies a selected Lite build and provider script; the Corral package's `components` map does not describe those. C4 publishes an immutable archive with the manifest plus all listed files, and reports the archive digest, raw manifest digest and exact commands. E1's build lock (`joint-lock-v1.schema.json`) records those digests, the independently built Lite revision and executable/asset digests, public seed and responder digests, and the resolved sandbox/runtime tool identities. The runner checks the lock's raw digest against an independent caller pin before use. These are inputs chosen by the acceptance runner, never adopted from a peer's hello. Use a clean, non-Git cwd and resolve only from the pinned package/fixture staging area.

Verify archive hash against the caller-supplied pin before unpacking. Allow one root `build-manifest.json`, exactly the component paths in its map, and their ancestor directories. Refuse path traversal, duplicate names, aliases, links, special files, extra/unlisted files and missing files. Reject duplicate JSON keys and unknown fields. Verify every entry's path, role, bytes, SHA-256 and executable bit, the three fixed entrypoint roles and executable bits, and actual platform/ABI prerequisites. Require the declared build recipe and exactly one prompt and one tool policy asset. The build recipe records exact build commands and dependency/asset provenance. Include the full Pi/JS dependency, runtime and asset closure in the package, and pin any system ABI dependencies and the host runtime/sandbox actually used in E1's lock. Verify the prompt digest as raw bytes, and tool policy both as raw asset bytes for custody and RFC 8785 bytes for the policy ref. In the joint lock, `lite.files` lists the package closure relative to the Lite package root; `lite.entrypoint` must be a listed executable. `runtime_tools` pins the actual sandbox executable and any separately provided interpreters/runtimes selected by the driver. Every mapped digest is over the exact file bytes. No dynamic search of HOME, PATH for product components, sibling repo, ambient dependency resolution, installation, config reload or download. Retain verified immutable staged inputs under a read-only mount through exec; verifying a mutable path and opening it later is insufficient. A `template`, unknown version, absent pin, changed registry/route, or any unmet prerequisite is fatal before executing a product component. Build dependencies are resolved before launch; the run itself is offline.

**Seed eligibility is a separate check from lock integrity.** The trusted runner must pin the exact reviewed `launcher-v1.json` digest in its release/build configuration independently of the joint lock and any caller-supplied pin (neither may configure or replace that profile pin). For the captured smoke the only eligible seed map is `seed_eligibility.captured.files` in that verified profile: the two notes linked by `T-2073:3`, taken from the specified Lite Git revision under `lite_source_prefix`. Its keys are the exact vault-relative paths (strip the source prefix); SHA-256 covers each raw Git blob including line endings. No sibling checkout is needed at launch. Before any product exec require `public_seed_files` in the lock **and** the actual staged initial vault file set and raw bytes to match this reviewed map exactly. Inspect the retained staging tree without following links or accepting path aliases; no extras, derived state, substitutes or arbitrary vault overrides. Keep the checked files protected from replacement through handoff. A correctly rehashed lock and matching caller pin cannot broaden eligibility. `public_seed_files` is a record of what was staged, not the authorization list.

The captured profile supplies no changed-operands variant. A changed-operands fixture needs separate Lite approval for the computed-capture path and its own reviewed allowlist of exact paths and raw digests, pinned independently by the trusted runner in a separate approved fixture profile. A lock, packet hash or successful captured run cannot grant either; refuse the variant until both prerequisites are present.

The runner is the verification authority for the complete joint lock and archive/component set; `joint_lock_sha256` is its attestation, not a request that a host resolve another product's files. The runner mounts the exact profile and Corral package manifest read-only at the two metadata paths in `launcher-v1.json` for **both** hosts. Each host rehashes these files against its privately provisioned enrollment pins, checks the manifest's profile pin, checks its own required local route/policy/entrypoint, and refuses mismatches. Lite need not see Corral's binaries, and Corral never sees Lite's package or vault. A runtime wire-registry mismatch is independently fatal before work/provider admission.

Run only with an explicit per-launch `--enable-public-fixture-e2e` switch plus a valid fixture build lock. The daemon's fixture entrypoint and Lite's first-party fixture entrypoint each enforce this; absent switch means no enrollment, endpoint, provider call or implicit restart. Generic Corral owner RPC, desktop startup and existing Lite MCP settings never activate it. Launch argv and fd slots in the profile are the C4/E1 interface; they refer to paths **inside** private mounts and numeric descriptors, not tokens or caller-selected commands. Explicit stop is closing the driver's per-host `lifetime` write end; no OS PID, private path, or extra transport power is returned to a UI. The driver can start hosts and exercise first-party operations; even though it establishes endpoints it must not keep a duplicate or transact peer messages to stand in for either product.

## Isolation baseline

Linux x86_64, non-root caller, no setuid/sudo fallback. Use rootless Bubblewrap or a conforming equivalent with verified unprivileged user, PID, mount and network namespaces, private `/proc` per sandbox, `no_new_privs` and no effective capabilities in payloads, and Landlock TCP ABI at least 4 on the sending supervisor. Refuse unavailable controls, including a failure to apply the intended restrictions. Mount only verified read-only inputs/runtime and private scratch, with separate Corral and Lite state roots, and show actual mount/namespace separation in a receipt. Lite alone gets the disposable fixture vault. Pi and shim get narrower private mounts with neither host state, vault, owner/home paths, nor owner/session sockets. Use empty private HOME/XDG paths and a small constructed environment (`LC_ALL`, `HOME`, `XDG_*`, `TMPDIR`, fixed `PATH`); no proxies, credentials, inherited config or unrelated descriptors. Null stdin and bounded diagnostics except the Pi–shim stdio pipe. Bound requests, allocation, time and process trees; the common driver owns the isolated PID namespace lifetime, per-component retained child identity and wrappers. A prior generation's uncertain child is not identified by searching cwd or a bare PID.

Use a dedicated loopback-only network namespace shared by the supervised provider transport and the scripted responder. Corral supervisor can connect only to the pinned TCP port, cannot bind TCP, and checks exact literal origin/path. The responder binds only the specified loopback socket. Deny IPv6 routes, all nonloopback interfaces/routes, UDP, raw and other non-required network families (e.g. AF_VSOCK) with a sandbox syscall policy; no externally connected inherited sockets. Use separate empty network namespaces for Lite, Pi and shim (no provider or general TCP); private inherited Unix channels remain usable across the namespaces. Shared numeric UID, chmod alone, or a loopback listener in the ordinary host namespace does not meet this contract. The trusted launcher and verified product binaries are in scope; this is not protection from a privileged host or an arbitrary hostile host process outside the fixture's namespaces. T-2070 demonstrated parts of this setup, not the joined launch, crash cleanup or production isolation.

## Enrollment and retained channels

No discovery or bind-by-path. The trusted offline launcher generates fresh random `link_id`, `lite_instance`, `corral_instance` and `channel_epoch` (128 bits each, base64url without padding), plus independently provisioned role-tagged copies of the verified pins. It creates unnamed, connected `AF_UNIX` socketpairs before exec, passes only each side's intended endpoints to the exact verified retained child role, closes extra copies before enabling I/O, and never uses the owner pairing socket/credential. The profile fixes the two endpoint types and FD roles. Each host gets a one-shot private `enrollment` pipe record with its expected peer, role, fixture/build pins and the epoch; check types, descriptor inventory and distinct socket identity before use. Those IDs are **labels not credentials**: authentication in this fixture derives from possession of the exclusive preconnected capability provisioned to the measured roles in separate process/mount sandboxes, not from an asserted ID, invoker UID, or `SO_PEERCRED` on a launcher-created socketpair (would identify its creator). Do not permit pathname join, opening another process's FD, uncontrolled ancillary passing or export to child env/argv. Fail closed if exclusive custody or peer identity cannot be established. At bootstrap each side compares a `link_ready` bootstrap record with the other side on the work FD before starting `hello`; validate role, both identities, protocol, epoch and profile/manifest pins against private enrollment, do not learn trust from the wire. Persist enrollment and pinned configuration before accepting starts. A fresh enrollment must never recover an old link's run. Revoke by durably fencing and retiring the link under the local admission gate and closing both channels; no new attachment may observe a revoked link as active. IDs for any new enrollment must be fresh.

Fixture v1 tests reconnection by **re-executing both hosts under the same live driver**, not by looking up a path or providing general FD handoff. On channel loss fence first. The driver must prove closure of the old endpoints and stop/reap of both old hosts and descendants before starting either replacement host (retain the same private durable stores, public vault, verified staged builds, link/instance IDs and pins). Re-execute with the same explicit fixture switch and new socketpairs and epoch; the private `enrollment` carries `prior_channel_epoch` (null for first enrollment, otherwise the previous epoch), and `link_ready` cross-checks it. Each host checks the previous epoch against its own persisted non-retired record and atomically records the new one before ready; reused epochs, mismatched stores, partial reconnect that cannot be proved, or driver death fence the run and block reattachment. Re-exec grants receipt reconciliation only for already admitted requests, not fresh dispatch, renewed leases or replacement generations. An exact retry of a committed start can still return the existing run; conflicting bytes do not start another. Fetch/ack and settlement remain subject to their existing independent fences. Unknown launch or consumption must be reconciled conservatively, not replayed.

The state/EOF fences apply during bootstrap as well as steady state. Close partially attached channels on error; they provide no grant and cannot be resumed.

- **Work**: one full-duplex connected stream per enrolled pair, hosts only. Each frame is `u32be payload-length` (not including length) followed by one strict T-2069 JSON object, 1–131072 bytes; reject length before allocation, partial/trailing payloads and duplicate/unknown fields, close on framing or routing violation. Both sides send `link_ready` first, before waiting for its peer. Then Lite's first request is `hello`, using the same envelope as all later operations: `{v:1,type:"request",id,op,params}`. Correlate it with `{v:1,type:"response",id,result}` or `{v:1,type:"response",id,error}`; `error` is the T-2069 code string. Corral writes its ready receipt after sending successful hello; Lite writes its receipt after verifying it and its recomputed policy ref. IDs are scoped by request direction and connection. Keep one in-flight request each direction; the bounded receive/correlation and incoming request handling must progress independently of an outbound request wait. Do not hold an admission lock across a reverse RPC; for example return the durable start snapshot without waiting for broker attach. Payloads/operations and direction follow T-2069 (including bidirectional `fence_session`). Never accept peer IDs from lifecycle params as authority. Disallow SCM_RIGHTS here. On EOF fence admission before any further work; negotiated reconnect cannot reset ledgers or extend a deadline.
- **Broker bootstrap**: hosts only, separate connected `SOCK_SEQPACKET`. After durable `bind_session` success, Corral offers distinct connected packet endpoints for `evidence` and `host_poll` to Lite in one `SCM_RIGHTS` message in that order, with the exact `broker_attach` binding record. Corral closes the copies sent to Lite, retaining the two opposite ends. Check exactly two new, distinct, connected `AF_UNIX/SOCK_SEQPACKET` FDs; close unexpected ancillary FDs, reject truncated control/data, binding mismatch, duplicate attach or foreign channels before broker use. Use non-inheritable received descriptors; acknowledge only after installing the immutable mapping under the active stop/generation/channel fence; `broker_attached` echoes the exact record with a new `type` and no ancillary data. Grant revocation/EOF invalidates both channels; broker connection never proves enrollment or renews a permit.
- **Shim and host polling**: Corral retains launch identity and passes only the evidence endpoint into the trusted stdio shim, plus a per-session private supervisor channel for trusted invocation metadata and the active binding (not a management endpoint). The Pi-facing stdio carries only pinned MCP initialization/list/call, not the private FD or metadata. The supervisor's trusted shim companion uses `host_poll` itself, so the shim's model-facing process does not have it. After `broker_attached`, negotiate on **each** of the two data FDs (evidence first, then host poll): one raw JSON-RPC object per packet for `initialize` → correlated reply → `notifications/initialized` (no reply) → `tools/list` → correlated reply, in that order using `startup` from T-2073:3 (transport IDs need not match the sample). Validate `2025-06-18`, exact descriptors, empty unneeded capabilities, and keep `read_result` host-only. These startup packets have no tool invocation identity. After negotiation, `tools/call` alone uses one T-2069 request or reply wrapper per packet (same 131072-byte encoded ceiling; no ancillary data or batches). Authorize purpose by FD and current binding, not by JSON fields or tool names alone. Serialize calls across both routes, one outstanding invocation total under the T-2073 ledger. Before forwarding an evidence call on stdio, the trusted dispatch adapter assigns its inner JSON-RPC ID and arms one private single-use tuple `(id,tool,invocation_id,args_digest)` with the shim. The shim acknowledges installation on the private control channel (echo the tuple exactly) before the adapter writes the stdio call; do not rely on send ordering across the two channels. Make at most one arm outstanding and bound the ACK and subsequent call by the current invocation and run deadlines. The shim independently validates the call, matches the inner ID, tool and recomputed digest to that tuple, and consumes it before forward; missing, repeated or mismatched arms cannot reach the ledger. An intentional replay re-arms the same invocation and digest with a fresh inner ID. Keep both trusted invocation fields off Pi stdio and deny unsolicited or unmatched replies. Only the supervisor's companion may allocate and issue host polls, keyed to pending calls it actually observed. No MCP finish_report, lifecycle, arbitrary server/config, discovery, or fallback. Once both private handshakes pass, allow gated Pi startup and its separate stdio negotiation with the shim; do not open tool dispatch or provider transport until that negotiation and pinned registry validation also pass.

Bootstrap records are strict single JSON objects (no duplicate or extra fields, T-2069 types), with exact keys and example values in `launcher-v1.json` under `bootstrap_examples`. `enrollment` is one bounded LF-terminated record then EOF; `link_ready` uses work framing; `broker_attach` / `broker_attached` each use a single bootstrap packet. `profile_sha256` is the raw `launcher-v1.json` digest, `corral_manifest_sha256` is the raw Corral build-manifest digest, and `joint_lock_sha256` hashes the exact joint-lock file (additionally pins Lite/responder/fixtures/toolchain). Dynamic sample IDs/digests are placeholders, never accept them as credentials or as product build locks. Compare all connection pins with retained launch state, including after restart. Pending or unresolved dispatch is accounted for using T-2069; neither a provider EOF nor replacing an endpoint proves no send.

## Readiness and provider

Each host sends exactly one LF-terminated JSON bootstrap result on its private `ready` pipe and closes it: `ready` means isolated build/pins verified, scripted route health attested by the driver, stores open, enrollment mutually validated and mandatory hello agreed; it does **not** mean a grant or generation exists. Driver waits on both pipes with a monotonic deadline; EOF without success, trailing data, wrong pin or a prematurely dead host fails. Start the provider first: signal `provider_ready` via a bounded private LF-terminated ready pipe then EOF after binding the fixed address; no HTTP probe billed as a turn. The provider and Corral each get their own private read end for the same per-launch bearer (lowercase hex for 32 random bytes, one LF then EOF); neither Pi nor Lite gets it. A host bootstrap failure may return only the `failed` record or close the ready pipe without success, never an exception or secret. Treat loss of the pinned responder while running as unavailable (no fallback).

Accept only `scripted / fixture-v1 / synthetic-local / external:false / demo-1` and the pinned prompt/tool policy. The trusted Corral transport (not Pi) owns exact `POST` to `http://127.0.0.1:43173/v1/chat/completions` with a fixture-only bearer pinned via the launcher-controlled private provider credential pipe. No ambient account lookup, DNS, proxies, redirects, SDK retries, compaction or implicit model calls. Use the bounded OpenAI-compatible SSE subset below as a route, not T-2070's captured transcript. The driver's pinned `scripted_provider` executable receives only its documented ready, lifetime and credential FDs; it stops on lifetime EOF. Verify the pinned fully rendered prompt and exact ordered model-visible registry on the **final** outgoing body; any automatic scratch `<cwd>` block must be removed by a pinned renderer/adapter before hashing, not ignored during verification. Reserve against that exact body and worst-case synthetic allowance, consume once at the actual I/O boundary after the current binding and permit/fence check, then settle under the upstream contract. Synthetic tariff/counters exercise accounting; no real billable credentials, routes, or spend. The happy script uses three provider turns: search; read the live source selector and request the approved metric (serialize the two tool calls); consume the actual read and terminal metric replies and issue `finish_report` with the actual released citations. For `pending`, the supervisor validates and receipts the terminal `read_result` reply against its pending invocation and result handle and uses that structured payload as the **original** `calculate_metric` tool result in the next model body (`tool_call_id` remains the original ID); never add a model tool, identity or extra turn for polling. Respect the pinned minimum 1000 ms and at most two new polls; if no terminal result fits the bounds, fail or report a limitation without pretending completion. If the approved metric selector is opaque per run, Lite supplies it as an explicit visible part of the approved question, never via hidden context or a test side channel. Do not hardcode response handles or the February operands/result into tool arguments or the report; assertions in the runner may of course use the expected cell. No further dispatch after a report commits. The responder is not a substitute broker, dispatcher, report store, or mechanism for seeding finished report bytes. Compare the final wire route/digest and actual send count in the receipt (not raw provider bodies).

The fixed POST uses `Authorization: Bearer <hex>`, `Content-Type: application/json` and one ≤262144-byte complete strict JSON object, closed at every layer. Top-level keys are `model:"fixture-v1"`, `stream:true`, `messages` and `tools`. Each tool is `{type:"function",function:{name,description,parameters}}` with pinned descriptors in order (`parameters` is the exact input schema). `messages` starts with `{role:"system",content:<pinned prompt>}` then `{role:"user",content:<exact approved question>}`. Each completed earlier step appends `{role:"assistant",content:null,tool_calls:[{id,type:"function",function:{name,arguments}}]}` (one element per issued call, `arguments` is a JSON string encoding the tool argument object), then one `{role:"tool",tool_call_id,content}` per call in issue order. Tool `content` is the UTF-8 RFC 8785 string of the validated structured payload, not the outer JSON-RPC wrapper or free text. A terminal host poll is substituted only as specified above. The responder verifies the exact prior call IDs/order and arguments against what it emitted, parses schema-valid payloads to drive the next expected step, and never accepts any hidden context. An expected happy payload that is missing, refused, or nonterminal fails the script; separate fault scripts may exercise these cases. Wrong method, URL, credential, malformed/over-limit body or unexpected script step gets non-2xx and no output tools. A successful reply is HTTP 200, `text/event-stream`, successive UTF-8 `data: <single JSON object>\n\n` records, then `data: [DONE]\n\n` and end of body. Use `provider.sse_example` for the single-choice `chat.completion.chunk` shapes: assistant role first; one complete function tool call per event with increasing zero-based indices (or content); one empty-delta terminal event with `tool_calls` (or `stop` for content). IDs are stable within a reply, call IDs unique in the conversation. No fragmented arguments, automatic retries, usage-only chunks, post-terminal content, or multiple choices. Bound SSE to 262144 bytes, 128 events and 32768 bytes per event, read by the run deadline; validate complete response before any resulting dispatch. Missing/invalid terminal data is ambiguous after send. For `demo-1`, the trusted transport meters a completed valid scripted exchange at a fixed synthetic 760 µUSD against a 1000 µUSD hold; absent valid completion is indeterminate at the full hold, and proven not sent is zero. This is a fixture tariff, not token metering or a claim about a live provider. Apply the pinned synthetic per-run/day/concurrency limits and the lower caller caps.

## Smoke and failure gates (design, not a measured run)

Run from a fresh mode-0700 directory outside any repository as a non-root user, with an empty environment except pinned tool locations; no Git, pane, daemon install or board. Unpack independently built packages, verify pins and namespace preflight, launch responder and both hosts, assert ready, then drive Lite's actual first-party approval/start → status → broker/turn → finish → fetch/verify/ack → inspect citation. Use the approved captured fixture (zero metric executions) first. Required fresh computation and a separately approved changed-operands run belong to Lite's distinct K6 disposition; do not imply their authorization by this launcher. Confirm the February report means `5100 − 2800 = 2300` in unspecified report units, not cash on hand. Confirm offline reopen from Lite's retained bytes after stopping Corral, without computation, authored writes or network. For this step close only Corral's lifetime and wait for its teardown. Work/broker EOF fences both sides against further disclosure, execution or dispatch; it does not terminate Lite's local retained-history inspector. Keep Lite and its vault available for the offline check **before** the final driver shutdown and disposal. Run negative variants at deterministic readiness/commit/handoff barriers, not sleeps. Test-owned hooks can report arrival and release a named barrier or force a pinned fail/drop/exit at that point inside the selected real component. For joined fault runs the driver may observe/release via a separate fixture-only harness channel to that component, explicitly pinned and absent on the normal smoke; carry only barrier identity/action, never broker, work, grant, permit or provider traffic. The driver must not relay, fabricate or replace authenticated peer messages. Machine-readable gate IDs and observable outcomes are in the launcher fixture.

Driver exits `0` only after every lane selected by the command passes and teardown is confirmed. A captured-only smoke may exit `0` with compute marked `not_run`/blocked; it cannot produce a full milestone pass. Full acceptance must not exit `0` with any required lane `fail` or `not_run`. `64` is invalid inputs/disabled choice, `69` unsupported environment/isolation, `70` startup or runtime/assertion failure, `74` unconfirmed teardown (takes precedence); nonzero never releases an acceptance pass. On global shutdown (normal exit, failed start, unrecovered timeout/peer crash, INT, TERM or driver lifetime EOF): fence both hosts, stop admitting provider/tool work, request ordered stop, close lifetime and broker FDs, then TERM/KILL only retained owned wrappers/groups after bounded grace; reap namespace init and descendants and verify they and listener/channel identities are gone. Keep `stop_requested`/quarantined slot until teardown proof, not merely parent exit, lost RPC or removal of a socket name. Outer driver death must close lifetimes and destroy namespace-owned descendants; test it from an outside harness that keeps retained ownership handles and performs safe containment if necessary. A subsequent driver must not adopt by PID or automatically enable an interrupted run. Do not remove scratch while children may still access it. On confirmed teardown, release private resources and erase only the uniquely owned disposable root (including vault/db/credentials), never shared or host directories; normal report retention remains until verified owner removal or this explicitly approved fixture disposal, not ack. For unconfirmed teardown quarantine and report the block. Emit only bounded sanitized evidence, with pass/fail/not_run per happy, fault, isolation and compute lanes, build/profile pins, time bounds, calls/turn/compute counts, custody/digest/cell coordinates and cleanup observations; no raw secrets, transcript, or ambient data.
